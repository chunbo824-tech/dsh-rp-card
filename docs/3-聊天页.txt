---
第 0 章 · 基础边界
H1 · 平台原生 DOM 的职责边界
平台原生生成的 DOM 结构由平台决定。CSS 可以控制其外观和布局，但不能凭空改变 DOM 结构、增加实际 HTML 节点或修改已有节点的属性。
如果需要改变结构或增加新的结构元素，必须通过框架允许的结构生成机制实现，不能把 CSS 当作 HTML 生成工具。
CSS 伪元素可以生成视觉内容，但不能代替实际 HTML 节点，也不能承担需要真实 DOM 结构才能完成的功能。
H2 · HTML 结构生成与 CSS 样式分离
需要新增、替换或重组 HTML 结构时，由正则替换负责生成 HTML。CSS 负责控制生成后 HTML 的外观、布局和交互表现。
二者职责不得混淆：
- 正则负责匹配原始文本、捕获内容和生成目标 HTML。
- HTML 提供实际 DOM 结构。
- CSS 根据实际 DOM 结构应用样式和交互规则。
不得要求 CSS 完成它本身无法完成的结构生成工作。
H3 · 交互机制按需引入
不同交互需求采用相应机制，不得为了统一而强制所有组件使用同一种交互结构：
- 独立展开、收起：可采用 "<details>"。
- 需要互斥切换：可采用已验证有效的 radio + ":checked" 机制。
- 需要根据 DOM 状态控制样式：可采用已验证有效的伪类机制。
- 只有实际需求需要时才引入唯一 ID 和关联属性。
不得为了使用某种技术而人为增加组件复杂度。

第 1 章 · 环境与能力识别
1.1 三种 DOM 来源
来源| 谁生成| CSS 权限| 典型形式
平台原生 DOM| 平台| 只能改外观，不能改结构| 消息容器、输入区、操作按钮组
正则生成 DOM| 正则替换| 只能改外观，不能改结构| 卡片、面板、折叠块
交互关联 DOM| HTML 与 CSS 共同构成| CSS 通过关联属性控制状态| radio 组 + 面板、label + input
同一个作品可以同时包含以上几类结构。
1.2 新能力确认方法
本节仅用于使用第 2 章容器清单、第 5 章正则清单之外的新容器、新选择器、新属性或新结构。
清单内已经记录且适用条件相符的能力直接调用，不必重复执行本节确认。
需要确认新能力时，按以下顺序执行：
1. 检查现有作品的 "built_in_css / builtCss" 字段，取得可用的实现证据。
2. 区分平台原生生成的容器与正则替换生成的容器。
3. 确认容器在实际渲染结果中是否存在。
4. 确认容器的实际层级、标签、属性和 class。
5. 确认目标选择器是否能够稳定匹配该容器。
6. 只使用已有证据支持的容器名和选择器语法。
执行边界：
- 使用已验证能力时，不要求重新探测平台 DOM。
- 使用清单外能力时，必须先取得实际结构证据。
- 不得为了完成能力识别而重复检查已经确认有效的基础能力。
- 不得将某个作品中的局部成功经验直接推断为其他环境中的既定能力。
1.3 能力的四类标注
类别| 含义| 处理方式
已验证有效| 在来源作品对应的平台环境中实际渲染生效| 满足原适用条件时可直接使用
尚未验证| 语法可能成立，但没有实际证据| 需要测试，不得当作既定能力
已知不支持| 在对应环境中尝试过但未生效| 不得作为该环境的可用能力
条件有效| 仅在特定环境、特定结构或条件下有效| 必须写明条件，不得无条件使用
已验证有效是指该能力已在来源作品对应的平台环境中实际渲染生效，不代表任何平台或任意版本均支持。
相同平台环境下，可依据已记录的适用条件直接复用。平台、版本或渲染机制发生变化时，必须重新判断原有条件是否仍然成立。
不得将未验证能力写成平台既有能力。
1.4 禁止清单
- 直接复制其他环境的容器名并假设当前平台支持。
- 根据 class 名称推断实际 DOM 层级。
- 根据视觉效果推断 HTML 标签。
- 将某个作品的容器列表当作全平台通用容器列表。
- 擅自增加未经验证的平台容器或 CSS 语法。
- 要求每次使用已验证能力时都重新执行 DOM 探测。
- 将条件有效的能力当作无条件有效的能力。

第 3 章 · DOM 与结构设计
3.1 结构生成职责
- 只需要改变外观：直接使用 CSS。
- 需要新增或修改 HTML 结构：设计正则替换。
- 需要交互：先确定交互机制，再确定是否需要唯一 ID。
3.2 实际结构识别
根据能力来源采用不同处理方式。
A. 已验证能力复用
使用第 2 章和第 5 章中已有的技术资产时，直接依据其已验证记录进行实现，不要求每次重新检查 DOM 或重复验证基础能力。
但必须遵守该能力记录中的适用环境、结构条件和已知限制。
B. 新能力确认
当目标需求涉及能力库中没有记录的容器、选择器、属性、层级关系或交互机制时，必须先取得实际结构证据，再设计对应实现。
需要确认的内容包括：
- 目标元素的标签名。
- 目标元素的层级关系。
- 目标元素上的属性和 class。
- 目标元素与相邻元素的关系（父子、兄弟、包含）。
禁止根据视觉效果推断 DOM 结构；禁止将某个作品的成功经验直接推断为其他环境中的既定结构。
3.3 HTML 生成职责
正则生成的 HTML 必须满足：
- 结构完整，标签闭合。
- 与实际选择器匹配。
- 不依赖 CSS 补全结构。
- 关联属性（如 "id / name / for"）正确写全。
- 需要交互时，确保结构顺序满足相应 CSS 选择器的匹配条件。
3.4 选择器与 DOM 的对应关系
选择器必须对应已确认的目标结构。
使用能力库内的选择器时，以已验证记录为依据；使用清单外选择器时，必须取得实际结构证据。
不得基于以下假设编写：
- 某个 class 一定存在。
- 某个层级关系一定成立。
- 某个属性一定被平台保留。
- 某个伪类状态一定能够触发。
写完新选择器后，必须在实际渲染环境中验证匹配结果。复用已有选择器时，重点验证其在本次组合中的效果。

第 4 章 · 正则替换设计
4.1 职责边界
正则负责：
1. 识别需要处理的原始文本。
2. 捕获需要保留的内容。
3. 定位需要插入或替换的位置。
4. 生成目标 HTML。
5. 在需要时向目标结构注入已有标识。
正则不负责：
- 生成复杂运行时状态。
- 执行 JavaScript 逻辑。
- 计算或递增唯一 ID。
- 推断原文中不存在的信息。
- 替代 CSS 完成样式控制。
4.2 通用设计原则
- 明确匹配起点与终点。
- 明确捕获组的职责。
- 优先保证原始内容不丢失。
- 处理换行、空格和可选分隔符时，必须以实际输入格式为依据。
- 识别相邻字段时，明确边界条件。
- 对多行内容使用与目标范围相匹配的跨行匹配方式。
- 根据目标文本的结构选择适当的捕获与替换策略。
- 避免不必要的贪婪匹配。
- 避免匹配范围吞并相邻内容。
- 不使用未经验证的正则语法。
- 调整已验证表达式时，只修改满足新需求所必需的部分，不随意破坏已验证的匹配边界。
4.3 边界策略是选择，不是规范
策略| 适用场景| 说明
捕获下一个段头作为终点| 需要保留下一段原文、避免 lookahead 时| 捕获组保留段头，替换时原样带回
使用前瞻表达式| 目标环境实际支持且测试通过时| 需确认目标引擎的正则能力
取到文本末尾| 只需处理最后一段时| 必须确认该段确实是文末段
不得将某一种策略强制应用于所有任务。通用段落切分方法与特定结构的边界匹配方法不必完全相同。

第 5 章 · 已验证正则清单
性质： 这是从四份作品中提取、经线上验证的正则能力资产，供模型直接调用。它是能力库，不是作品模板。
使用方式： 模型根据目标需求从清单中选择正则范式，并结合当前作品的实际字段名和结构判断是否需要调整捕获组、匹配边界和替换文本。
已验证表达式应优先保持原有实现。只有当新需求确实要求改变匹配范围或输出结构时，才调整必要部分。
部分表达式采用占位符表示，属于范式说明，不是可以不经替换就直接执行的完整正则。实际使用时必须将占位符替换为目标作品中的真实字段、字面量或 class 名称。
5.1 内容定位与段落切分
范式 A：用“下一个段头”界定本段
段头A[ \t]*\r?\n([\s\S]*?)(\r?\n段头B[ \t]*[:：]?[ \t]*\r?\n)
- 匹配目标：以段头 A 开始、到段头 B 之前的内容。
- 捕获组职责：
  - 组 1 = A 段内容。
  - 组 2 = B 段头，替换后必须原样保留。
- 替换结果：把组 1 替换为 HTML，组 2 原样带回。
- 适用条件：需要保留下一段原文。
- 已知限制：不适用于最后一段（无下一段头）。
范式 B：子卡切分（用“双换行 + 段头”双重界定）
(^\|\r?\n)[ \t]*\*\*[ \t]*子卡标题A[ \t]*\*\*[ \t]*\r?\n([\s\S]*?)(\r?\n[ \t]*\r?\n[ \t]*\*\*[ \t]*子卡标题B[ \t]*\*\*[ \t]*\r?\n)
- 匹配目标：以 "** 子卡标题 A **" 开始、到 "** 子卡标题 B **" 之前的内容。
- 捕获组职责：
  - 组 1 = 前置空行。
  - 组 2 = A 段内容。
  - 组 3 = B 段头。
- 适用条件：需要处理子卡嵌套。
- 已知限制：需要严格的“双换行 + 段头”格式。
范式 C：取到文末
段头[ \t]*\r?\n([\s\S]*)
- 匹配目标：以段头开始、到文末的内容。
- 捕获组职责：组 1 = 内容。
- 适用条件：只需处理最后一段。
- 已知限制：必须确认该段确实是文末段。
5.2 标记与字面量替换
成对标记内内容替换
<标记A>([\s\S]*?)</标记A>
- 匹配目标：成对标记内的内容。
- 捕获组职责：组 1 = 标记内内容。
- 替换结果：把内容替换为 HTML 结构。
- 适用条件：需要把成对标记转为 HTML。
字面量清除
^- 字面量标记[ \t]*\r?\n?
- 匹配目标：固定字面量标记。
- 替换结果：替换为空。
- 适用条件：需要把元数据从显示中隐藏。
5.3 关键词着色
关键词A → <span class="着色类A">关键词A</span>
关键词B → <span class="着色类B">关键词B</span>
- 匹配目标：固定关键词。
- 替换结果：用 span 包裹关键词，CSS 通过着色类控制颜色。
- 适用条件：需要给特定关键词上色。
- 执行顺序：必须在结构切分之后，避免被结构切分误吞。
- 特别注意：如果某关键词还有更具体的匹配（如“关键词＝N”），必须先执行具体匹配、后执行裸关键词匹配，否则会被提前包进 span，导致具体匹配失败。
- 如果某个具体匹配已经由数值进度条规则处理，则应先完成进度条转换，再执行对应的裸关键词着色。
5.4 数值进度条
以下为数值进度条的档位匹配范式。实际使用时，将“关键词”“进度条”“档位”替换为目标作品中的真实关键词、class 和替换内容。
空态：
(关键词)[＝=]占位符
替换：
$1 <span class="进度条 空态"></span>
0～9 档：
(关键词)[＝=](0|[1-9])([^0-9]|$)
替换：
$1 <span class="进度条 0档"></span>$3
10～19 档：
(关键词)[＝=](1[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 10档"></span>$3
20～29 档：
(关键词)[＝=](2[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 20档"></span>$3
30～39 档：
(关键词)[＝=](3[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 30档"></span>$3
40～49 档：
(关键词)[＝=](4[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 40档"></span>$3
50～59 档：
(关键词)[＝=](5[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 50档"></span>$3
60～69 档：
(关键词)[＝=](6[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 60档"></span>$3
70～79 档：
(关键词)[＝=](7[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 70档"></span>$3
80～89 档：
(关键词)[＝=](8[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 80档"></span>$3
90～99 档：
(关键词)[＝=](9[0-9])([^0-9]|$)
替换：
$1 <span class="进度条 90档"></span>$3
100 档：
(关键词)[＝=](100)([^0-9]|$)
替换：
$1 <span class="进度条 100档"></span>$3
匹配与替换说明：
- 匹配目标：关键词 + 等号 + 数值。
- 捕获组职责：
  - 组 1 = 关键词。
  - 组 2 = 数值，用于定位档位。
  - 组 3 = 数值后第一个非数字字符，或文末空匹配；替换时必须带回。
- 替换结果：关键词 + 对应档位的进度条 span + 原有后缀。
- 适用条件：需要把数值显示为可视化进度条。
- 已知限制：空态与 0 档是不同语义，CSS 侧要区别处理。
边界要求：
1. 数值档位必须按实际数值范围匹配，不能让 "10" 被误判为 "1"，也不能让 "100" 被误判为 "10"。
2. 数值规则必须保留数值后面的原始非数字字符，避免替换时吞掉相邻标点或分隔符。
3. 0～9、10～19、20～29 等档位表达式应按具体规则执行，不得将未验证的简写表达式直接当成完整规则。
4. 空态占位符必须替换为目标作品实际使用的空态标记。
5. 如果目标作品的数值范围、档位划分或分隔符与本范式不同，必须依据实际输入格式调整，不得直接套用。
5.5 双分支匹配
段头[ \t]*(?:([^\n段标记]+)|\r?\n([^\n段标记]+))
- 匹配目标：段头后同行内容，或段头后换行内容。
- 捕获组职责：组 1 或组 2 二选一命中。
- 替换结果：使用 "$1$2" 兼容两种布局。
- 适用条件：需要兼容同一字段的两种排版格式。
重要语义说明：
表达式中的：
[^\n段标记]+
是字符类，表示逐字符排除其中列出的字符，并不是排除完整字符串“段标记”。
因此，该表达式会排除换行符以及字符“段”“标”“记”本身。不得将其解释为字符串级别的段落边界匹配。
如果目标字段内容可能包含上述字符，必须先核对原始表达式的实际适用条件。若新任务需要排除完整段落标记，应重新设计边界表达式，而不是沿用错误的字符串级解释。
本表达式保留为来源作品中的既有范式，不得在没有验证的情况下将其推广为通用段落切分规则。
5.6 唯一 ID 注入
(?<=<ID:[ \t]*([a-z0-9-]+)>[\s\S]*?)目标段[ \t]*\r?\n([\s\S]*?)(\r?\n下一段[ \t]*\r?\n)
- 匹配目标：在唯一 ID 标记之后、目标段内、到下一段之前。
- 捕获组职责：
  - 组 1 = 已有唯一 ID。
  - 组 2 = 目标段内容。
  - 组 3 = 下一段头。
- 替换结果：把唯一 ID 注入目标结构的 "data-turn-id / id / name / for" 属性。
- 适用条件：需要互斥切换的组件，例如状态终端、任务面板。
- 已知限制：需要目标引擎支持该表达式使用的变长后顾及对应捕获行为。
引擎适用条件：
该表达式保留为来源作品对应正则引擎中的已验证实现，不代表所有正则引擎均支持。
迁移到其他引擎时，必须单独确认：
- 变长后顾是否受支持。
- 后顾中的捕获组是否受支持。
- 跨行匹配行为是否符合预期。
- 捕获组编号与替换文本是否保持一致。
如果目标引擎不支持该表达式，不得直接声称它是通用可运行正则。必须根据实际引擎能力重新设计等价实现并测试。
5.7 执行顺序（硬约束）
顺序| 规则类别| 理由
1| 带唯一 ID lookbehind 的注入替换| 必须先执行，否则 ID 标记可能已被清除
2| 普通段落切分| 先确定结构边界，避免后续替换影响段落定位
3| 标记 / 字面量替换| 在结构范围确定后处理固定标记
4| 其他具体关键词或字段匹配| 先处理包含附加信息的完整表达式，避免裸关键词提前包裹
5| 数值进度条转换| 在裸关键词着色之前处理关键词 + 数值组合
6| 裸关键词着色| 处理尚未被具体规则转换的普通关键词
7| 去唯一 ID 标记| 最后清除元数据，避免影响前面的 ID 注入
补充要求：
- 若某个具体关键词规则与进度条规则处理的是同一段 "关键词＝数值"，以实际承担该转换的具体规则为准，不得重复转换。
- 不得将裸关键词着色提前到具体字段或进度条转换之前。
- 如果某种作品结构需要不同的执行顺序，必须说明其边界条件，并实际验证整个正则链的最终结果。
- 执行顺序应以正则替换的真实运行顺序为准，不能只按规则文档中的章节顺序推断。

第 6 章 · TURN_ID 与关联机制
6.1 适用条件
只有当组件确实需要跨结构关联、互斥切换或依赖伪类状态控制时，才引入唯一 ID。
场景| 是否需要唯一 ID
radio 互斥面板需要通过唯一 name 区分不同消息中的选择组| 需要
label 与 input 关联，需要对应 id 和 for| 需要
CSS 需要通过轮次标识区分不同消息中的交互结构| 需要
普通静态组件| 不需要
独立 "<details>" 折叠组件| 不需要
TURN_ID 是可选能力，不是每条消息、每个组件都必须具备的固定字段。
6.2 职责划分
角色| 职责| 不做的事
AI| 根据实际组件需求生成唯一 ID；确保同一消息中需要关联的结构使用同一个 ID；确保不同消息中的互斥组不会发生 name 冲突| 不直接写入最终 HTML 的 id / name / for 属性
正则| 匹配 AI 已生成的 ID；捕获 ID；将 ID 注入目标 HTML 属性| 不生成、不递增、不计算、不擅自修改 ID
HTML| 在需要的位置使用对应的 id / name / for 等属性；保证关联关系正确| —
CSS| 使用实际注入的属性和伪类进行选择；不假设所有消息或组件都有 TURN_ID| 不硬编码具体 ID 值
6.3 ID 一致性要求
- 同一关联组件中的相关属性使用同一个 AI 生成的标识。
- 不同消息中的互斥组具有独立的 "name"。
- "label[for]" 必须能够找到对应的 "input[id]"。
- 不需要交互关联的组件不引入多余标识。
- 注入正则先于相关标记清除正则执行。
- CSS 使用后缀匹配（如 "[id$="-target"]"），不硬编码具体 ID。
- 一个组件内部的 radio 组应使用对应的唯一 "name"，不同组件实例之间不得共用同一互斥组名称。
- "data-turn-id" 可以用于轮次隔离和结构标识，但不能代替 radio 的 "name" 隔离，也不能代替 label 与 input 所需的 "id / for" 关联。
6.4 禁止
- 不得将 TURN_ID 写成所有消息的必需输出。
- 不得为了“统一”而给不需要互斥的组件也注入唯一 ID。
- 不得让正则承担 ID 生成或递增职责。
- 不得让 CSS 硬编码某一次实际生成的 ID 值。
- 不得假设只有 "data-turn-id" 就能自动建立所有关联关系。

第 7 章 · 纯 CSS 交互
7.1 独立折叠
使用 "<details> / <summary>" 实现独立展开与收起。
适用条件：
- 各个折叠区域互不排斥。
- 用户可以独立打开多个区域。
- 不需要跨组件互斥控制。
不需要为普通独立折叠引入 TURN_ID。
核心 CSS 要点：
- 去除原生 marker："summary::-webkit-details-marker { display: none; }" + "summary::marker { content: ""; }"。
- 通过 "details[open]" 与 "details:not([open])" 区分展开/折叠态。
- 自定义指示符号通过伪元素实现，不依赖浏览器默认三角。
7.2 互斥切换
使用 radio + ":checked" 和兄弟选择器实现互斥切换。
适用条件：
- 同一组内容只能有一个选项处于激活状态。
- 需要通过纯 CSS 控制显示与隐藏。
- 实际 DOM 结构能够满足选择器关系。
必须检查：
- radio 是否属于正确的同一组。
- "name" 是否正确隔离不同组件实例。
- "id" 与 "for" 是否对应。
- 选择器能否匹配实际 DOM 层级。
- 默认选中状态是否符合需求。
- radio 与目标面板是否同级且 radio 在前（"~" 兄弟选择器生效的前提）。
需要 TURN_ID。
7.3 伪类状态控制
保留已验证有效的 ":has()"、":checked" 等伪类用法。
必须明确：
- 仅在实际需求适合时使用。
- 必须确认目标平台的渲染环境支持。
- 必须针对实际 DOM 结构测试选择器。
- 不得假设任意复杂的 ":has()" 组合都已经得到验证。
- 已验证的具体伪类用法可以直接复用，但不能将其推广为任意组合均有效。
CSS 中通过伪类匹配状态时，用后缀选择器匹配注入的 ID（如 "[id$="-target"]:checked"），不需要感知 ID 具体值。
7.4 机制选择原则
先确定交互需求，再选择技术。
- 不得为了统一而强制所有交互组件采用 radio。
- 不得为了避免 ID 而放弃确实需要互斥切换的结构。
- 独立折叠与互斥切换不得混淆。
- 已有交互机制可以满足需求时，优先复用，不重复设计新的交互系统。
7.5 可拓展项
行动建议栏可附加一键复制按钮，通过平台原生复制代码（非 JS）实现。
属可选能力，不强制。

第 8 章 · CSS 设计
8.1 选择器设计原则
1. 已验证选择器优先直接复用；清单外选择器必须先确认目标 DOM 结构。
2. 优先使用目标环境中已验证有效的选择器语法。
3. 选择器应尽可能明确，避免无意影响其他组件。
4. 样式应根据组件实际职责组织。
5. 需要跨消息隔离时，使用已经验证的标识机制。
6. 不依赖 JavaScript。
7. 不假设 CSS 能够创建不存在的 HTML 结构。
8. 不使用未经验证的平台专属容器名或选择器。
9. 优先复用已验证有效的完整选择器；当需要覆盖已有样式时，再按照 8.2 处理级联优先级和特异性。
8.2 CSS 优先级与样式覆盖
CSS 不仅需要选择正确的 DOM，还必须确保目标样式能够有效覆盖平台原有样式和其他组件样式。
设计时必须同时考虑 CSS 级联优先级、选择器特异性、"!important" 和声明顺序。
8.2.1 优先级判断
CSS 样式是否生效，不能只看选择器是否匹配，还必须考虑：
1. 声明的重要性：普通声明与 "!important" 声明。
2. 样式来源：平台样式与自定义样式的来源及优先关系。
3. 级联层级：声明所属的 cascade layer 及其优先关系。
4. 选择器特异性（Specificity）。
5. 作用域接近度：目标环境使用 "@scope" 等机制时，需要考虑对应规则。
6. 同等条件下的声明顺序（Source Order）。
在本框架常见的普通样式覆盖场景中，可以按以下方式进行实际判断：
- 先确认样式来源、重要性和级联层级。
- 再比较选择器特异性。
- 如果适用，再比较作用域接近度。
- 前述条件相同时，才由声明顺序决定结果。
不得简单认为选择器写得更长就一定能够覆盖目标样式，也不得认为增加 "!important" 就能解决所有覆盖问题。
特别注意：
- "!important" 会改变级联中的优先关系，不是简单地给选择器增加一个固定权重。
- "!important" 声明之间仍然需要比较来源、级联层级、特异性等条件。
- 同一来源内，重要声明的级联层顺序与普通声明存在相反关系，不能只按普通声明的层级直觉判断。
- 普通声明无法仅凭提高选择器特异性覆盖重要声明。
- 动画、过渡等具有特殊级联优先级的机制不应被忽略；若目标环境存在相关冲突，应单独判断。
8.2.2 "!important" 使用原则
"!important" 是解决已确认样式冲突的工具，不是默认书写规范。
允许考虑使用的情况：
- 平台原有样式具有更高的实际覆盖优先级。
- 已有选择器无法在合理范围内覆盖目标样式。
- 同一组件存在必须强制统一的关键视觉属性。
- 线上测试已经确认普通声明无法实现预期效果。
使用要求：
- 只给确实需要强制覆盖的属性添加 "!important"。
- 不得无差别地给整个组件的所有属性添加 "!important"。
- 不得为了避免分析优先级而给所有 CSS 声明添加 "!important"。
- 不得在没有实际冲突证据时滥用 "!important"。
- 修改已有样式时，优先检查原声明与目标声明的级联优先关系，再决定是否需要增加 "!important"。
- 已经使用 "!important" 的规则，应检查是否会妨碍组件后续状态样式和主题样式正常生效。
8.2.3 选择器特异性
当目标样式未能覆盖已有样式时，按以下顺序处理：
1. 确认目标选择器实际匹配。
2. 确认冲突声明是否处于相应的样式来源、重要性和级联层级。
3. 检查现有规则是否具有更高特异性。
4. 在不扩大影响范围的前提下，适当提高目标选择器特异性。
5. 检查是否存在作用域接近度等其他适用的级联条件。
6. 在其他条件相同的情况下，检查 CSS 声明顺序。
7. 如果仍然无法可靠覆盖，再考虑使用 "!important"。
禁止为了提高优先级而无意义地堆叠 class、ID 或复杂后代选择器。
提高特异性必须同时考虑作用范围，不能为了覆盖一个局部组件而使规则意外影响其他消息或组件。
8.2.4 CSS 声明顺序
对于来源、重要性、级联层级、特异性和其他相关级联条件均相同的声明，后出现的规则通常覆盖先出现的规则。
因此：
- 同一属性存在多个冲突声明时，必须检查实际定义顺序。
- 新增样式时，应避免无意覆盖已经生效的组件样式。
- 修改现有样式时，应优先处理原有冲突声明，而不是不断追加重复规则。
- 不得假设 CSS 文件中的书写顺序能够覆盖特异性更高或级联优先级更高的规则。
- 对于重要声明，不能直接套用普通声明的级联层顺序判断方式。
8.2.5 实际覆盖验证
关键样式必须检查最终渲染效果，而不能只检查 CSS 代码。
至少验证：
- 目标属性是否真正生效。
- 是否被平台样式覆盖。
- 是否被其他组件样式污染。
- "!important" 是否造成后续样式无法正常覆盖。
- 是否影响其他消息或组件。
- 默认状态与交互状态下的样式是否都正确。
最终原则：
优先通过准确的选择器和合理的级联关系解决覆盖问题；只有在确实需要时才使用 "!important"。
8.3 样式作用范围
- 样式规则具有明确的作用范围。
- 相互独立的组件避免不必要的选择器耦合。
- 公共样式与组件专属样式适当分离。
- 修改某个组件时，应检查是否影响其他组件。
- 避免重复定义和无效规则。
8.4 组件隔离
- 不同组件的样式选择器不应互相污染。
- 组件内部状态（展开、选中、悬停）应通过组件自身的属性或伪类表达，不依赖全局状态。
- 同一条消息内的多个组件不应互相干扰。
- 不同消息之间的同类组件不应互相干扰（需交互隔离时用 ID 后缀匹配）。
- 静态组件不应为了隔离而引入不必要的 ID。
8.5 平台原生消息容器的内层透明处理
本规则仅适用于第 2.1 节记录的平台原生消息容器，不构成其他平台或其他组件的通用要求。
对于 "#customized-question-content"、"#customized-answer-content" 等消息本体，内部的 "div"、".markdown-body"、"#customized-answer-content-markdown" 等层应根据实际结构透明处理：
- 背景透明。
- 边框无。
- 阴影无。
- 颜色和主要背景效果只挂最外层。
目的是避免多层背景叠加、边框重影和阴影重复。
8.6 背景图与气泡不透明度适配（bg_image / bg_mobile）
本作品不产出背景图资产：平台字段 bg_image（电脑端）与 bg_mobile（手机端）由作者在平台填写图片 URL，CSS 不写死任何 URL、不依赖具体导出键名（历史版本曾用 bg_img / back_img / mobile_bg，映射以当前平台导出配置为准）。
设计要求：平台提供给玩家调节消息气泡的不透明度滑块。当滑块降到 0 时，页面背景图必须完整可见，不能被任何自绘图层遮挡或压暗。
气泡「半适配」的实现边界：
- 内层一律透明：#customized-answer、#customized-answer-container、#customized-answer-content-container、#customized-answer-content-markdown、.markdown-body，以及玩家消息对应层，背景透明、无边框、无阴影。
- 气泡本体（#customized-answer-content / #customized-question-content）的底色只作为兜底，必须带守卫，不得无条件覆盖：
  #customized-answer-content:not([style]),
  #customized-answer-content[style=""] { background: …; }
  平台一旦把背景或不透明度写进内联 style，上述选择器即不再命中，外观交还平台滑块。
- 不得对气泡本体使用不带守卫的 background、backdrop-filter 或大面积半透明遮罩：前者会让滑块失效，后两者会模糊、压暗背景图。
- 气泡框保留 background-clip: padding-box 与 overflow: clip，避免底色溢出圆角或在子层露边。
- 边框与阴影保持低对比；当平台用内联 opacity 淡出时整块自然淡出，用内联背景色时仅底色变化，此时细边框是唯一残留，必须浅到不构成残影。
- 页面层面禁止整页不透明底色或铺满的遮罩层；输入区底部渐隐层必须过渡到透明，不得用实色块盖住画面下缘。
- 装饰伪元素（纹理、高光）只能是低透明度点阵或线性渐变，且 pointer-events: none，不得整块填充遮挡背景。
验收（人工）：把气泡不透明度调到 0，背景图在桌面与手机宽度下均完整可见、无残影、无模糊带；调到中间值时气泡底色按平台滑块变化，不出现双层叠加。
8.7 工具按钮状态层
目的：让同一张卡里的消息操作按钮与页面工具按钮表现一致，而不是每个按钮各写一套。只统一「状态表现」，不统一「视觉风格」——配色仍由各卡决定。
适用范围：仅第 2.3 节已登记的操作按钮 ID、页面工具按钮 ID，以及分页的属性锚点。清单外按钮先登记再使用。
实现方式（令牌优先）：把状态写成 CSS 变量，只挂在清单内选择器上；新按钮套用同一组变量，不复制整段规则。
--btn-fg：默认前景色
--btn-fg-hover：悬停前景色
--btn-fg-disabled：禁用前景色
--btn-opacity：默认不透明度
--btn-opacity-active：按下不透明度
--btn-opacity-disabled：禁用不透明度
--btn-duration：状态过渡时长
状态矩阵（所有清单内按钮共用）：
默认：前景用 --btn-fg，不透明度用 --btn-opacity，背景透明，不改边框宽度。
悬停：前景用 --btn-fg-hover，不透明度 1；过渡时长用 --btn-duration，只过渡 color、opacity、background-color、border-color。
按下：不透明度用 --btn-opacity-active。
禁用：前景用 --btn-fg-disabled，不透明度用 --btn-opacity-disabled。
焦点：不写 focus 规则，保留平台默认。禁止 outline: none 或其他等价删除；确需自定义时只允许 :focus-visible，且必须给出可见焦点提示。
属性白名单：color、background-color、opacity、border-color、filter、transition，以及对应的 -webkit- 兼容写法。
不得改动：display、flex 相关、width、height、padding、font-size、line-height、position。平台原生按钮的内部布局由平台决定，改了会破坏图标与文字的对齐。
禁止事项：
- 用 MUI emotion 动态类（如 button.css-xxxxx）作锚点：哈希随构建变化，失配时静默失效且作用域不可控。
- 用单一类名或按钮标签选择器批量套用：会命中不打算修改的按钮。
- 对整组按钮无差别写 filter: none !important：平台可能用 filter 表达加载、禁用等状态，强行清空会吞掉状态区分。
- 用 prefers-color-scheme 单方面把按钮强制成深色而不同时处理卡片与正文：会出现深浅混搭。
新增按钮的接入顺序：先在 2.3 登记 ID 与语义 → 再套用同一组变量 → 最后在真实消息里验证默认、悬停、按下、禁用四种状态；平台默认焦点行为不改。
8.8 视觉设计自由
框架不负责规定具体作品的视觉风格。
未来作品可以采用不同的布局、配色、材质、装饰和排版方案。
框架只约束实现方式必须符合已经确认的平台能力、结构边界和技术机制。
不得把某个作品的完整视觉方案、配色或组件组合固化为所有作品必须采用的模板。

第 9 章 · 工作流程
本框架以已验证能力库为基础开展设计。
默认优先复用已验证的容器、正则表达式、HTML 结构生成机制和 CSS 选择器，不要求每次任务重新分析平台 DOM 或从零验证已有能力。
只有当现有能力库无法满足目标需求时，才进入新能力调查和验证。
第一步：明确设计需求
根据用户要求确定：
- 需要实现什么视觉效果。
- 需要哪些组件。
- 是否需要新增 HTML 结构。
- 是否需要独立折叠或互斥切换。
- 是否涉及跨消息隔离。
- 是否需要修改平台原生容器。
- 是否涉及对已有样式的覆盖。
先明确目标，不先进行无目的的平台探测。
第二步：从已验证能力库选择实现资产
根据目标需求，直接查阅：
- 第 2 章：已验证容器清单。
- 第 5 章：已验证正则清单。
- 第 7 章：已验证纯 CSS 交互机制。
- 第 8 章：CSS 设计及优先级规则。
优先使用已有验证记录的容器、选择器、正则范式和交互机制。
使用要求：
1. 已验证的容器名称保持原值，不擅自改名。
2. 已验证有效的选择器优先直接复用。
3. 已验证有效的正则表达式优先复用，根据新作品的字段结构调整必要部分。
4. 已验证有效的 HTML 与 CSS 机制可以作为实现基础。
5. 不得为了追求所谓的通用性而放弃已有的可靠实现。
6. 必须遵守相应能力记录中的适用条件，不得将局部验证结果无条件泛化。
第三步：组合实现方案
根据目标组件组合已有技术资产：
- 只需要改变平台原生容器外观：直接使用已验证的容器选择器和 CSS。
- 需要新增 HTML 结构：选择已验证的正则范式生成 HTML。
- 需要独立折叠：使用已验证的 details 机制。
- 需要互斥切换：使用已验证的 radio + ":checked" 机制。
- 需要跨消息隔离：按需使用 TURN_ID。
- 存在样式覆盖冲突：按照 CSS 优先级规则处理。
不需要重新发明已经存在的实现。
第四步：处理新需求与能力缺口
只有当现有能力库无法满足目标需求时，才进入新能力处理。
分为三种情况：
A. 已有能力可以通过调整组合满足
直接组合已有能力，不新增技术机制。
B. 已有能力需要适当扩展
在保留已验证部分的基础上，修改必要的匹配条件、捕获组、替换内容或选择器。
扩展时应尽量保持原有已验证行为不变，并对本次修改部分进行验证。
C. 需要使用清单中没有的容器、语法或机制
不得自行假设其存在或有效。
必须取得实际 DOM、源码或线上测试证据，再决定是否引入。
新能力未经验证前，标记为尚未验证，不得混入已验证能力清单。
第五步：生成完整 CSS 与正则
按照确定的实现方案输出完整代码。
检查：
- 是否复用了正确的容器名称。
- 正则是否使用正确的匹配边界和捕获组。
- HTML 结构是否完整。
- TURN_ID 是否仅在必要时使用。
- CSS 选择器是否对应目标结构。
- 是否存在级联优先级冲突。
- 是否存在重复声明或不必要的 "!important"。
- 正则执行顺序是否符合第 5 章规定。
- 是否保留了原始文本中不应被替换的内容。
- 是否存在未经验证的语法或结构假设。
第六步：验证实际效果
对于已经验证过的技术资产，重点验证本次组合后的整体效果，不必重复证明每项基础能力。
重点检查：
- 目标样式是否生效。
- 是否发生样式覆盖。
- 新增 HTML 是否正确生成。
- 交互是否正常。
- 多个组件是否互相干扰。
- 多条消息之间是否正确隔离。
- 是否破坏原有样式或结构。
- 原始文本是否出现丢失、截断或错误吞并。
- 关键样式在默认状态和交互状态下是否均生效。
如果出现问题，优先检查本次新增代码与已有能力的组合关系，而不是立即推翻已经验证的基础机制。
第七步：更新能力记录
只有实际测试通过后，才能将新能力加入已验证能力清单。
记录：
- 新增或修改的容器、选择器、正则或交互机制。
- 实际验证环境。
- 实际验证结果。
- 适用条件。
- 已知限制。
区分已验证有效、尚未验证、已知不支持和条件有效。
不得将一次作品实现成功直接解释为所有环境均有效。
不得为了记录新能力而重复复制既有资产，或无必要地建立平行能力清单。

框架总原则
1. 优先复用已验证能力。 不重复发明已有技术，也不要求每次任务重新探测已确认的平台结构。
2. 能力资产与作品模板分离。 保留具体容器、正则、选择器和交互机制；不固化某一作品的完整视觉方案。
3. 结构由 HTML 提供。 正则生成或替换 HTML，CSS 控制已有结构的外观与交互。
4. 交互按需设计。 独立折叠使用 details，需要互斥时使用 radio + :checked，只有需要关联或隔离时才引入唯一 ID。
5. 新能力必须有证据。 清单外能力不得凭空假设；经过实际验证后才能加入能力库。
6. CSS 覆盖必须考虑级联。 不能只比较选择器长度，不得滥用 !important。
7. 验证最终组合效果。 已验证的基础资产不必每次重复证明，但本次新增代码及组合结果必须检查。
8. 保持实现最小化。 能通过已有能力组合解决的问题，不新增平行机制，不人为增加结构和复杂度。
