# 资料库（同人 / 改编 / 参考材料 → 世界书）

**读取前提**：用户表示要做既有作品的同人或改编，或已经提供参考材料时，才读本文件并启动该流程。普通原创卡不读、不启动。

---

## 一、它是什么，不是什么

它是一次制卡之前的前置阶段：把用户提供的材料整理成**可回查的资料库**，再按用户需求**取舍**成世界书条目，同时把有视觉价值的部分单独留存给第二、三部分。

不是这些：

- 不是一键出卡。资料库只产出世界书条目与视觉参考，不写主提示词、不写开场白。
- 不是全文塞入。世界书有预算，必须取舍。
- 不自动联网补资料。
- 不替原文补设定。

位置：在第一部分之前完成，产出的 `wb` 直接进入第一部分的交付物。

---

## 二、触发与入口

由提示词判定，用户不需要记任何命令。

触发条件（满足任一即启动）：

1. 用户说明作品是既有作品的同人、改编、续写、二创（「做一张某某的同人卡」「按这部小说改编」）；
2. 用户提供了小说正文、剧本、设定集、游戏文本等参考材料（目录里的文件或对话附件都算）；
3. 用户要求「按原作做」「按这个材料做」。

不触发（防误触）：

- 只有「同人」两个字，没有指向既有作品、也没有材料：「做一张原创卡，不要同人梗」不触发。
- 否定语境：「不要同人」「别用原作设定」不触发。
- 泛指：「想做点有同人感的卡」不触发，按普通原创卡处理。

材料缺失时的处理：

```text
用户：做一张《XXX》的同人卡。
插件：要做同人卡，需要原作材料我才不会写偏。你可以把小说/剧本/设定集放进工作区，
      或直接发附件给我；不想提供的话，我就按原创卡做。
  上传 → 继续流程
  不传 → 取消该流程，按普通原创卡做，不再追问
```

取消后不保留任何资料库文件。

---

## 三、材料读取

两种来源都要支持：

| 来源 | 处理方式 |
|---|---|
| 工作区目录里的文件 | 直接读 |
| 对话附件 | 先落盘到 `.card-build/library/sources/`，再按文件读 |

落盘规则：

- 保留原文件名与扩展名，登记来源路径；
- 判定编码（UTF-8 / GBK / GB18030 / Big5 / UTF-16），乱码先转码再处理；
- 记录文件哈希，后续重跑据此判断材料是否变化；
- 材料文件只读，任何整理结果都不写回原文件。

## 四、材料类型与切分

| 类型 | kind | 默认切分 | 抽取侧重 |
|---|---|---|---|
| 小说正文 | `novel` | 章节正则（第X章/回/卷/节/部/篇；Chapter N；纯数字） | 人物、地点、事件、规则 |
| 影视剧剧本 | `screenplay` | **默认按集**，单集超过块上限再按场切 | 场景、动作描述、对白风格、人物关系 |
| 游戏设定集 | `setting-book` | 已有条目结构优先，不强行按章节切 | 规则、势力、地域、物品；少归纳、多照抄 |
| 游戏文本（对白/日志） | `game-script` | 按章节或任务 | 世界规则、任务链、势力关系 |

切分要求：

1. 切分后先给用户看**切分预览**（章/集列表与前几行），确认后再抽取；
2. 过小的块合并到相邻块，避免碎片；
3. 块大小按上下文容量定，超过上限再切；
4. 标题重号保留，不合并、不重编。

剧本按集/按场的判断：单集文本在块上限内 → 按集；超出 → 该集按场切，并在条目里记明「第X集 第Y场」。

## 五、多来源与优先级

多份材料并存时：

| 优先级 | realm | 说明 |
|---|---|---|
| 最高 | `canon` | 原作正文、官方设定集 |
| 中 | `reference` | 官方补充资料、访谈、周边设定 |
| 低 | `fanon` | 同人作品、二手整理 |
| 最低 | `unknown` | 来源不明 |

规则：

- 同层级冲突：**两份都留**，标 `conflict`，写进 `conflicts.md`，不自动选边；
- 不同层级冲突：以高优先级为准，但低层级内容保留为条目，不进常驻；
- `fanon` 内容无法标记为 `canon`；混用必须在条目里写明。

## 六、目录与文件

```text
.card-build/
  state.json                  现有状态机，新增 library 段
  library/
    sources/                  材料原件与登记表（只读）
      <source-id>.txt
      <source-id>.json
    records/                  资料条目，人可编辑
      <record-id>.md
    index.jsonl               索引，可从 records 重建
    plan.json                 预算与分配结果
    batches.json              批次与用量账本
    visual.json               视觉参考清单
    conflicts.md              未决矛盾
    library-proposal.md       方案文档（走审批）
    visual-proposal.md        视觉参考交付文档
```

三层分开：**材料（source）→ 资料条目（record）→ 世界书条目（wb）**。任何一层都不覆盖上一层。

## 七、字段定义

### 7.1 材料 source

| 字段 | 说明 |
|---|---|
| `id` | 稳定 ID，如 `novel-a`、`screenplay-2024` |
| `kind` | `novel` / `screenplay` / `setting-book` / `game-script` |
| `title` | 材料名 |
| `realm` | `canon` / `reference` / `fanon` / `unknown` |
| `continuity` | 世界线，如 `novel-main` / `anime-2024` / `game-route-A` |
| `edition` | 底本或修订版本 |
| `phase` | 最早可用于创作的阶段，未知填 `null` |
| `file_sha256` | 原件哈希 |
| `rights` | 默认「仅本卡内整理，不含再分发」 |

### 7.2 资料条目 record

| 字段 | 说明 |
|---|---|
| `id` | 小写字母数字短横线 |
| `kind` | `character` / `place` / `faction` / `rule` / `event` / `relationship` / `item` / `visual` / `question` |
| `name` / `aliases` / `body` | 名称、别名、Markdown 正文 |
| `realm` / `continuity` | 继承来源，可覆盖 |
| `known_from` | 最早可揭示阶段，`null` 表示全程可用 |
| `status` | `confirmed`（原文明写）/ `inference`（合理归纳）/ `uncertain`（存疑） |
| `evidence` | `[{unit_id, source_sha256, quote, start}]`，**必填** |
| `conflict` | 有矛盾时填写，并登记进 `conflicts.md` |
| `base_sha256` | 修改既有条目时必填，用于防止覆盖人工修改 |

### 7.3 视觉参考 visual

| 字段 | 说明 |
|---|---|
| `id` | |
| `kind` | `scene`（场景构图）/ `costume`（服饰）/ `item`（器物）/ `palette`（配色）/ `style`（质感风格） |
| `source` | 来自哪份材料的哪个位置 |
| `use` | `profile`（第二部分）/ `chat`（第三部分）/ `both` |
| `note` | 一句话：这里能借什么 |
| `rights` | 仅作参考，不直接使用原件 |

## 八、流程

```text
P0 导入     识别材料类型，登记身份/版本/阶段，落盘与哈希
P1 切分     编码判定 → 按类型切分 → 切分预览 → 用户确认
P2 抽取     按分类抽成资料条目，带原文摘句、阶段、确定性
   ■ 停点一：确认条目清单（有哪些人物、地点、规则、事件）
P3 方案     产出 library-proposal.md：两套取舍方案 + 预算 + 视觉清单
   ■ 停点二：用户选 A 或 B → 审批通过（propose / approve-design）
P4 写入     生成世界书条目，跑校验
P5 视觉     单独交付 visual.json + visual-proposal.md，单独确认
P6 报告     来源范围、条目数、预算占用、未决矛盾、视觉清单
```

两个停点与方案审批都是硬性门禁：未确认条目清单不写世界书；方案未批准不写入；视觉参考未确认不交给第二、三部分。

## 九、抽取

### 9.1 分类

| 分类 | 默认 | 产出 kind |
|---|---|---|
| 总纲（世界规则/时代背景） | 开 | `rule` |
| 人物 | 开 | `character` |
| 地点 | 开 | `place` |
| 势力 | 开 | `faction` |
| 事件 | 关 | `event` |
| 物品 | 关 | `item` |
| 剧情分段 | 关 | `event` |
| 文风 | 关 | 只产一段文风描述，进 `ppt`，不进世界书 |
| 视觉 | 关 | `visual`，进 visual.json |

每个分类必须配一个示例条目，否则输出格式会漂。

### 9.2 抽取纪律

1. 每条必须有原文摘句，没有证据的不许入库；
2. 不补造：缺章不补、重号不合、结局不编；
3. 矛盾保留：两处不一致就两条都留，标 `conflict`；
4. 阶段必标：后期信息 `known_from` 不能为 `null`；
5. 同人不能冒充原作：`fanon` 条目不许标 `canon`；
6. 设定集类材料少归纳、多照抄，避免把条目式知识改写走样。

### 9.3 深度三档

| 档位 | 抽什么 | 批次 |
|---|---|---|
| 快速 | 总纲 + 主要人物 + 主要地点 | 1–3 批 |
| 标准（默认） | 加势力 + 关键事件 | 按材料长度 |
| 深读 | 加剧情分段 + 人物演变 + 视觉参考 | 按材料长度，先跑样本 |

长材料必须先跑 1–2 个代表单元，测出质量与实际用量，再决定后续批次。

## 十、取舍

### 10.1 四类去处

| 去处 | 判据 | 落到哪 |
|---|---|---|
| 常驻 | 每轮都要用：世界基本规则、核心人物核心设定 | `wb` |
| 条件触发 | 提到才需要：配角、具体地点、具体事件、细节规则 | `wb`，内容锚 |
| 只做背景 | 影响氛围但不该占预算 | 不写世界书，或并进 `ppt` 一句话 |
| 丢弃 | 与卡无关、重复、矛盾未决、纯装饰 | 留档不进卡 |

### 10.2 两套方案，用户选一套

方案文档必须同时给出两套，由用户选，不许插件自行决定。

| | 方案 A · 沉浸优先 | 方案 B · 轻量优先 |
|---|---|---|
| 常驻占预算 | 约 70% | 约 40% |
| 触发条目 | 少而精 | 多而细 |
| 适合 | 世界规则复杂、氛围重要 | 剧情推进快、细节多 |
| 代价 | token 高、易撞预算上限 | 世界感薄、需玩家主动提及 |
| 展示内容 | 常驻合计字数、触发条目数、预算占用 | 同上 |

两套基于同一份资料库计算，区别只在分配倾向。

### 10.3 预算

```text
1. 复杂度判定：资料条目 ≥ 24 或用户明确要求 → 复杂档（常驻 1600 / 单条 900）
   否则 → 简单档（常驻 800 / 单条 600）
2. 常驻按优先级分配：世界基本规则 → 主要人物核心 → 势力/地点总览 → 事件细节
3. 超预算时降级顺序固定：事件细节 → 地点细节 → 人物细节 → 规则细化
   核心规则与主要人物不降级
4. 剩余预算给条件触发条目，单条不超上限
```

### 10.4 触发映射

| 记录类型 | 触发源 | 锚点 |
|---|---|---|
| 人物 | 内容锚 | 姓名 + 主要别名 |
| 地点 | 内容锚 | 地名 + 常用简称 |
| 势力 | 内容锚 | 组织名 |
| 规则 | 常驻，或格式字段锚（种族/职业等枚举） | 字段取值 |
| 事件 | 内容锚 | 事件名或关键词 |
| 结算/结束类 | 格式标记锚 | `END` 等精确标记 |

触发词必须与档案页实际采集的取值逐字一致。

### 10.5 阶段门控

- `known_from ≤ 开局阶段`：可常驻；
- `known_from > 开局阶段`：只能条件触发，内容前缀注明「此信息此刻尚不可知」；
- `null`：视为全程可用。

后期内容不得进入常驻。

## 十一、视觉参考

### 11.1 抽什么

| 类型 | 来源 | 交给 |
|---|---|---|
| 场景构图 | 地点/环境的原文描写 | 第二部分（背景图、地图） |
| 服饰 | 人物衣着描写 | 第二部分（立绘）、第三部分（配色） |
| 器物 | 关键道具描写 | 第二部分（装饰） |
| 配色 | 材料反复出现的颜色词 | 两部分统一 |
| 质感风格 | 整体调性 | 第三部分（材质、边框） |

### 11.2 交接方式

- 视觉参考不进世界书；
- 走独立交付：`visual.json` + `visual-proposal.md`，单独确认；
- 第二部分开工时只读已确认的 `use=profile|both`；第三部分读 `use=chat|both`；
- 只作为**提示词依据**，不直接使用原图与封面（版权）。

## 十二、状态与断点

`state.json` 新增：

```text
library: {
  sources: [],
  depth: 快速|标准|深读,
  stage: P0..P6,
  batches: { used, max, calls, tokens },
  confirmed: { records: false, proposal: false, visual: false }
}
```

规则：

- 写入前校验 `base_sha256`，不符则停下，不覆盖人工修改；
- 人工改过 `records/*.md` 后重建索引，不读旧索引；
- `resume` 从下一批继续，已入库不重做；
- 冲突写入保留双方，不自动选边。

## 十三、校验

| 编号 | 检查 | 时机 |
|---|---|---|
| LIB001 | 资料条目缺原文证据 | P2 |
| LIB002 | 常驻条目 `known_from` 晚于开局 | P4 |
| LIB003 | 常驻合计或单条超预算（复用 WB102 文案） | P4 |
| LIB004 | 触发条目没有有效锚点 | P4 |
| LIB005 | 视觉参考未标 `use` 或用途 | P5 |
| LIB006 | 存在未处理矛盾条目 | P4 |
| LIB007 | `fanon` 内容被当 `canon` 写入常驻 | P4 |

全部按三段式报错：问题 → 原因 → 两条可行路线。

## 十四、与四部分的边界

| 部分 | 资料库给它什么 |
|---|---|
| 第一部分 | 世界书条目（`wb`）、文风描述（进 `ppt`） |
| 第二部分 | 视觉参考中 `use=profile\|both` 的部分 |
| 第三部分 | 视觉参考中 `use=chat\|both` 的部分，以及正文段落结构建议 |
| 第四部分 | 无直接输入；若面板要展示世界内数值，可参考 `rule` 类条目 |

资料库不写 `ppt`、不写开场白、不写页面代码。

## 十五、交互话术

用户只需说两句话：

```text
我上传了一部小说，帮我做成资料库，用来做卡。
```

```text
这部作品我只用前两卷，后面的先不要。
```

流程中最多问三件事：

1. 材料身份：原作 / 官方补充 / 同人 / 不确定；
2. 剧透范围：用到哪一卷、哪一集；
3. 深度：快速 / 标准 / 深读。

其余按默认走，只在异常时报告。

## 十六、验收

| 项 | 标准 |
|---|---|
| 可回查 | 随机抽 3 条世界书条目，都能定位到原文摘句 |
| 阶段正确 | 开局常驻里没有后期信息 |
| 预算合规 | 常驻合计与单条均不超档 |
| 锚点有效 | 每条触发条目在档案页取值里能找到对应词 |
| 矛盾透明 | `conflicts.md` 与实际矛盾一致，未被静默合并 |
| 视觉可用 | 每条视觉参考都能说出「借什么」，且标注用途 |

## 十七、本版不做

| 不做 | 原因 |
|---|---|
| 自动联网抓资料 | 来源不可控、版权风险、需额外授权链 |
| 全库塞进世界书 | 预算不允许 |
| 语义向量检索 | 平台不提供，承诺了做不到 |
| 自动决定取舍 | 取舍由用户在两套方案中选择 |
| 直接使用原图/封面 | 版权；只用文字描述做参考 |

| 阶段 | 内容 |
