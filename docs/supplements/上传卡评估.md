# 上传卡评估与优化（card_review）

用户把自己做的卡（平台导出的 JSON）交进来，要求「看看哪里有问题」「优化逻辑」「为什么这么占上下文」时用。**不要走 card_build 四部分流程，也不要让用户重做卡。**

工具不调模型：读入、审计、预算、前后对比、导出由代码做；改写由 agent 做，写完交给 `apply` 复检。

## 〇、规范依据（评估前先读对应章节）

- **四部分规范**：`docs/1-写卡提示词.txt`（世界书触发、常驻预算、状态机）、`docs/2-档案页.txt`（前端/展示）、`docs/3-聊天页.txt`（CSS 与正则）、`docs/4-变量面板.txt`（面板模板、JSON、商品索引这类前端数据）、`docs/5-成人向补充.txt`（尺度与代理边界）。
- **评估框架**：工作区根 `角色卡评估框架.md`（准入 G1–G3、五模块评分、N/A 规则）；打分工具是 `card_evaluate`，本流程复用它背后的 `lib/evaluate.js` 硬指标审计。
- **审查清单**：`docs/supplements/审查清单.md`。
- **代码复用**：`lib/core.js` 的 WB / RGX / CSS / CUE 校验与 `lib/evaluate.js` 的 `auditCard`；工具本身**不读文档**，文档由 agent 在评估/改写前阅读。

## 一、流程与闸门

```text
status → ingest（file / text）→ audit → plan → apply → export
```

| 动作 | 做什么 | 闸门 |
|---|---|---|
| `status` | 看阶段与下一步 | 无 |
| `ingest` | 读卡、识别格式、归一字段、存 `.card-build/review/source.json` | 无 |
| `audit` | 结构 / 体量 / 逻辑三层机械检查，写 `audit.md` | 已 ingest |
| `plan` | 按必修 → 建议 → 可选排序，写 `plan.md` | 已 audit |
| `apply` | 接收 agent 改写后的补丁或整卡，重新审计、写 `compare.md` | 已 plan |
| `export` | 生成可导入的 v2 文件与 `review-report.md` | 已 apply |

硬性规则：

- **audit 之后必须先把结论讲给用户看。** 用户只要评估：做到 `audit` 就停（需要优化清单可以再 `plan`，`plan` 只出方案、不改卡）。用户明确要优化：`plan` → 用户确认方案 → 改写 → `apply`。顺序不要跳。
- `apply` 会重跑审计：**新增必修问题默认拒收**。只有用户明确表示接受风险，才带 `force: true`，报告里会留记录。
- 重新 ingest / 重新 audit 会作废并删除下游产物（方案、改写版、导出件）。这是有意的：所有结论必须基于同一份卡，也避免误导入旧文件。
- 手工改 `source.json` 或 `optimized.json` 会被摘要校验拦住，需重新 ingest / apply。
- 连续改写（第二次 apply）基于**当前优化版**合并，不会丢掉上一次的改动。

## 二、读入与格式

- 平台每次导出会**独立随机**抽一套同义键名（同一张卡 2 小时内导出 3 次，键名集合都不同、值一致）。完整同义词池与证据见 `references/platform-fields.json`（权威字段库）与 `docs/supplements/平台键名对照.md`。内容键全部要能读：例如 `pre_pt` / `pre_prompt` / `ppt` / `prpt`、`pretxt` / `pre_text` / `ptx`、`posttxt` / `post_tx` / `potx` / `suffix_txt`、`dsc` / `intro` / `description` / `descr`、`builtCss` / `bicss` / `inner_css`、`regex_rp` / `rrep`；手机背景 `bgmob` / `bg_m` / `bg_mb`，桌面背景 `bg_image` / `back_img`。
- **尊重导出件原字段名**：原卡的键名是作者/平台的契约，审计只按别名读取、不改名，优化只改内容；导出优先沿用原结构。非 v2 标准键源导出为 `card.optimized.source.json`，`cover` / `tag_list` / 语言 / 界面设置原样保留；v2 源生成 `card.optimized.v2.json`，标准 40 键之外的未映射/未知键也会原样追加，不静默丢弃（平台是否接受额外键需导入实测）。不要为了“规范”强行改名或转 v2。
- 容忍 BOM、数组、`{ card | data | result | payload }` 包装。
- `wb` / `rgx_rep` 是**整组替换**；补丁里只放要改的字段，没出现的字段保持原样。
- 未登记别名：`ingest` 会把原卡未识别的键写入 `<作品目录>/.card-build/alias-suggestions.json`（本机候选表，`.gitignore` 忽略，不进包）。确认后按需补进 `lib/core.js` 的别名/登记表并加测试，再发布框架；候选表本身不随版本发布。
- 平台导出可能缺字段：`ps_chats` / `preset_chats`（预设对话，平台界面里仍在但导出可能为空）、`cvr_tiny`（封面缩略）。这类字段不能靠导出件恢复，报告里只作为「可能发生的情况」记一句（让用户导入后自行检查、必要时补设）；`记录.md` 那种完整调查记录不要发给用户，用户问起再解释。
- 平台随机键名组合里的设置键：**登记（能理解）≠ 映射（导出到 v2 键）**。完整清单与同义词池见 `references/platform-fields.json`；标签（`labels`/`lbls`/`tag_list`/`tags`/`tg`）只读、不产出（平台机械规定），自动总结（`summary_config`/`ai_s_config`/`ai_summary_config`）只读、不参与导出。未确认语义的键（`chk_tag`/`ctny`/`tmp_val`/`type`/`card_type`/`ps_type`/`tp`/`preset_ch`/`v_mode`/`vp_mode`/`ui_flag`/`ext_cfg`/`image_bk`/`kind`/`ianp`）只登记为已知，不猜映射。

## 三、审计覆盖

复用的既有校验：`WB*`（世界书）、`RGX*`（正则）、`CSS*`（聊天页样式）、`CUE009/011/013/014/015`（内容安全与代理边界）、`CUE017/018`（模板派/正则派冲突与锚点）、`X1`（AI 区触发词子串碰撞）、`ENV`（HTML 不安全写法）。

上传卡特有编号：

| 段 | 编号 | 含义 |
|---|---|---|
| 结构 | RV001–RV008、RV234 | 缺卡名/主提示词/后置词、缺【时间地点】、wb 不是数组、未识别字段；RV234：字段读成空但原卡有疑似同义的未识别键（别名缺失） |
| 体量 | RV101–RV116 | 主提示词过长（RV101）、前后置词过长（RV102）、常驻超预算（RV104）、常驻单条超长（RV105）、完全重复条目（RV106）、同 key 不同正文（RV107）、正则未标 only_render（RV108）、提示词重复行（RV109）、变量面板配置（RV110/111）、展示层体积（RV113）、空正文（RV115）、停用条目（RV116） |
| 逻辑 | RV201–RV210、RV227–RV234、RV236–RV237 | 正文含自身触发词（RV201，间接风险，info；平台不直接扫描正文）、每轮误加载（RV202）、触发词出现在 ppt（RV203）、非法正则触发词（RV204）、状态机空承诺（RV205）、$1 无捕获组（RV206）、depth≠0（RV207）、probability≠100（RV208）、不安全写法（RV209）、嵌套量词风险（RV210，启发式）、规则放错层（RV227）、触发词结构/重复（RV228）、世界书正文写运行期识别/防守性命令（RV229）、同正文不同触发词（RV230）、长条目疑似可拆（RV231）、同一 key 父子触发词冗余（RV232）、世界书与前端/面板层重复（RV233）、空字段/别名缺失（RV234）、世界书内部重复样板段（RV236）、跨层重复候选（RV237，只提示先问） |

触发面判定是**启发式**：

- 先按 `key_region` 判断扫描哪一侧：2=玩家输入，4=AI 输出，6=两者。
- 再按 `value_region` 判断注入位置：1=提示词，2=前置词，4=后置词。`ptx` / `post_text` 是注入字段，不是消息文本，不能拿来代替 `key_region` 的触发面。
- AND 条目要求所有词都出现；OR 条目命中一个就算；正则条目抽出字面量再判断。
- 因此常驻数字是「最小保证」而不是平台实测值。
- 常驻预算按卡型：简单卡 800 / 复杂卡 1600 / 大世界卡（世界书 ≥80 条或显式 `complexity: large`）6000–8000；单条上限分别 600 / 900 / 1200。

三类必须人工判断、不能机械处理的情况：

- **改触发词**（RV202）：先判断这段文本运行时是否每轮都需要。格式/状态/路由规则必须常驻，改成稀有词会让它缺场；只服务某场景的知识才换内容锚。拿不准就标出来问用户。
- **拆长条目**（RV231）：先确认运行时 AI 是否确实只用到其中一部分。各节有独立触发条件或互斥场景才拆；每次触发都要整篇的，拆开会导致漏载。
- **去重**（RV230）：先判断两处是否会在同一轮同时在场。互斥条件下各自自包含，重复是必要的；同时在场且语义相同才是真重复。
- **父子词**（RV232）：依据 `docs/1` 模块四「子集关系天然覆盖」与「关键词越短越可靠」——同一 key 里短词包含于长词时，长词不会带来额外触发面；只留子集词或父级词之一，符号丢失要修复符号，不要用内文替代。
- 上传卡不一定使用四部分模板：如果后置词里有「【玩家输入】/ PREFIX PROMPT / POSTFIX PROMPT」且没有【时间地点】，按「玩家输入定义型后置词」处理，不套用 RV005/RV006 的框架段落要求；如果世界书里已有 IDLE/CONTINUE/END 或状态机判定，也不再报 RV205 空承诺。不要把四部分约定强加到原卡自己的玩法流程上。
- 开场白为空不是错误：有的前端初始化页会在内部生成开场指令并复制给玩家。`audit` 会做静态检查——`desc` 里有 `navigator.clipboard` / `clipboard.writeText` / `execCommand('copy')` / 复制按钮等复制能力时，视为已由前端处理，静默；没有检测到时不报错，只把问题放进 `questions`，先问用户「网页是否已经内置开场指令并带有复制功能」。不要直接补开场白，也不要报错。
- **RV228 格式锚**：含空白或标题符号的触发词先与 ppt / ptx / post_text / ai_v_prompt 的输出格式比对。`字段：` 对应 `- 字段：`、`** 字段 **：值` 对应 `** 字段 **：<枚举>` 时视为精准格式锚，不报“空格写坏”；只有找不到对应格式，或空格/冒号写法不一致时才提示。
- **格式/状态判断只给思路**：插件不预设字段名，也不自动推断状态。AI 应自己找卡片规定的输出字段：触发词含空格/冒号/标题符号时，与卡片自己的格式比对，一致就不报；正文只服务某地点/状态而触发词是通用行为词时，提示“可能同时触发”；触发词是卡片规定格式时，只有内容与条目不一致才报错。
- **RV236 内部重复**：同一段长文本在 3 条以上世界书里重复（常见于每条原子数据都重抄同一主规则），聚合为一条提示并估算可省字数；结构化原子记录不报 RV233 面板重复。
- **RV237 跨层重复**：自动比对 `ppt` / `ptx` / `post_text` 的长段与近似段，只给候选，不自动删；会生成一个待确认问题，先问哪些是“靠近玩家输入的必要重复”、哪些是纯复制。确认前不要 apply 改动。
- **RV210 是启发式**：只对高置信嵌套量词报 warning；「换行 + 空白类」的常见任务面板写法（如 `(?:\r?\n[ \t]*)+`）会豁免，不再误报。低置信的嵌套量词只给 info，先实测再决定改不改。

## 四、体量与优化方向（不宣称平台消耗）

```text
输入（当前轮） = ppt + ptx + 本次玩家输入 + post_text + 触发世界书 + 变量提示词
历史 = 用户设置的历史消息条数（玩家输入、AI 输出各自算一条）
历史文本 ≈ 玩家消息数 × 玩家输入字数 + AI 消息数 × AI 输出字数
每轮输入 ≈ 当前轮 + 历史文本
输入体量单位 ≈ 字符 × 1.0–1.7（CJK，内部相对量）
输出（最低量）≈ post_text 字符 × 1.0–1.7（AI 每轮要照着模板写状态栏；实际正文更长）
```

- 玩家输入字数默认 100、AI 输出字数默认 1000，可传 `player_input_chars` / `ai_output_chars` 覆盖；这两个是估算参数，不是平台账单。
- 历史消息数：`memory_rounds` > `memory_setting` > 状态里的值 > 默认 5 条；**不再把设置值除以 2**。
- `ai_summary: true` 时历史固定按 1 条计。

## 五、改写守则

改写前先做**全作品评估**：通读 `ppt` / `ptx` / `post_text` / `desc` / `built_in_css` / `rgx_rep` / `ai_variable_tmpl` / `ai_v_json` / `ai_v_prompt`。先确认问题属于哪一层、改哪一层；前端/面板已经实现的数据（商店索引、列表、表单）不要在世界书里重复生成（RV233）。

然后逐条回答三个判断，答不清就先问用户：

1. **触发词**：这段文本运行时是否每轮都需要？是 → 保留常驻触发词，优先压缩体量，不要为了省体量改成稀有词；只服务某场景 → 改成内容锚；拿不准 → 标出来问用户。
2. **拆分**：拆之前确认运行时 AI 是否确实只用到其中一部分。各节有独立触发条件或互斥场景才拆；每次触发都要整篇的，拆开会导致漏载，不要拆。
3. **重复**：先判断两处是否会在同一轮同时在场。互斥条件下各自要自包含，重复是必要的，不要合并；同时在场且语义相同的，才是真重复。

可以改：压缩重复、合并同义、去重条目、补缺字段、重排顺序、改锚词、把细则外置成按条件加载的世界书、补 `replace_text` / `is_only_render`。

不要改：世界事实、角色设定、剧情走向、尺度档位、玩家代理边界；不要为了让审计好看而删掉必要规则；不要编造平台未验证的行为。

改写完成后：

- 大卡或二次测试：先 `audit` 做全局评估，再按字段组（`ppt` / `ptx+post_text` / `wb` / `desc+CSS+正则` / 变量面板）逐组改写并 `apply`；每改一组先看 `compare.md`，确认没有新增必修问题再改下一组，不要一次性全改。
- 只交改动字段（推荐）或整卡 JSON；数组整组替换。
- 先自己对照 `plan.md` 检查，再 `apply`。
- `apply` 会重新审计；新增 error 会被拒收。拒收时按提示修，不要直接 `force`。
- 导出前确认用户已备份原卡：平台导入是**整卡覆盖**。

## 七、常见问题

**用户只发了一张图/一段文字，不是 JSON。** 告诉他先到平台导出 JSON；本工具只处理结构化卡。不要猜字段。对话附件先落盘到工作区（如 `.card-build/review/upload-<name>.json`），再把实际路径交给 `ingest`。

**字段名不认识。** 先看 `source-meta.json` 的 `unknownKeys` 与 `topKeys`；确认是卡但键名不同，就把缺失的别名补进 `lib/core.js` 的 `FIELD_ALIASES`，并加测试。

**审计全是 warning，没有 error。** 正常：上传卡多半能跑，问题在逻辑与体量。按 plan 的 P1 处理，不要为了凑 error 硬报。

**用户嫌报告太长。** 只讲三件事：体量最大的三处、最该先修的三处、改完大概能省多少（相对量）；细节让用户自己看 `audit.md`。

**平台导入后行为不对。** 先确认导入的是 `card.optimized.v2.json` 且是整卡覆盖；再核对平台设置（标签、简介、BGM、封面等）是否需要在平台补设；最后检查正则与触发词。不要声称「工具已验证」。
